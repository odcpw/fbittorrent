## P1-16d — Reconciliation preserves active verification (fbt-v2i)

Branch `ntm/fbittorrent/cod_4-p1-16d`, based on the orchestrator's main snapshot.

Queue decisions now distinguish active initialization from a check cancelled
through the existing `check_cancelled` marker. Active checks are not unpaused:
unpause closes their run and can restart validation. The decision retains this
classification from the same stats snapshot used to plan running intent, so a
check finishing between planning and application waits for a fresh post-check
policy decision. The next normal maintenance pass unpauses an admitted,
initialized torrent. Explicit Stop still drains hashing, marks it cancelled and
shows stoppedDL; a later Start can resume that stopped check.

The new tests reuse P1-16c's filesystem counters without modifying its source
or assertions. The test module includes that unchanged file in the same module
namespace and adds a child module which can wrap its real filesystem factory.
The outer wrapper gates the second real 16 KiB read. Two threads each complete
16 reconciliations while that read remains blocked, asserting stable handle
and initialization identity, no cancellation and unchanged physical IO counts.
No synthetic payload or hash result is returned by the wrappers.

- Incomplete restore: one admission and one full two-piece check total
  `[creates,reads,bytes] = [1,2,32768]`. The real first piece verifies, the second
  deliberately fails its hash; after checking, 16,384 bytes are complete and the
  torrent runs as stalledDL. No storage recreation occurs.
- Explicit recheck: after the initial check above, the requested operation adds
  exactly one admission and one two-piece check, reaching `[2,4,65536]` total.
  Its newly admitted handle survives all concurrent reconciliations and runs
  after verification. The 32-pass gated control runs during each check.

The fork's scan progress advances at piece entry; while the second read is
held it reports 32,768 scan bytes, whereas the physical counters report only
one completed read / 16,384 bytes. The test asserts both exact observations.

The existing `test_app` helper now runs the same one-second maintenance tick as
production startup. Its former one-shot reconciliation could leave a restored
seed paused after checking once active unpause was correctly deferred. The
helper treats owner cancellation as normal and fails unexpected maintenance
errors. Existing test functions, transfer deadlines and expected states remain
unchanged. No production owner/teardown path was edited.
