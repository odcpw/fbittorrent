## P5-06 — Have-bitfield snapshot accessor

Bead: `fbt-p5-06-bt4`. Branch: `ntm/fbittorrent/cod_2`.

`ManagedTorrent::have_pieces_snapshot(&self) -> Option<Box<dyn BitV>>`
copies the chunk tracker's verified have-bitfield inside `with_chunk_tracker`.
Both existing read locks remain held until the owned copy is complete; the
returned in-memory bitfield retains no tracker/storage borrow or lock. `BitV`
is re-exported at the crate root so consumers can name the public return type.
The fork provenance README documents this deviation and its MSB-first byte
layout, final-byte padding and state behavior. Initializing/tracker-less states
return None; an initialized paused tracker still supplies its verified bits.

The three native fork unit tests add private, disposable torrents to real
sessions with DHT, trackers and discovery disabled. Their on-disk data has every
third piece deliberately corrupt, so actual SHA-1 verification produces known
mixed have bits. The 10-piece case verifies bytes `6d 80`, including the six
padding bits. Mutating/flushing a snapshot leaves a fresh tracker snapshot
unchanged; the returned copy remains readable after dropping the torrent handle
and session. Initialization admission is held to observe paused initialization
deterministically. The explicit tracker-less transition/error observations are
controlled unit states, not claims about a live UI or network transfer.

All commands use the normal rch shim, `CARGO_BUILD_JOBS=4` and five private XDG
directories. Logs below are under `target/test-logs/fbt-p5-06-bt4/`. Each named
snapshot test prints piece count, elapsed nanoseconds, presence, byte count and
set-bit count. Missing bitfields report null counts. The retained Python log
collector converts these observations into E.1 per-case JSONL with final
verdicts; the original Rust test output is also preserved.
