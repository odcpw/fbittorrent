# P1-02b — resumed-transfer completion timeout

Bead: `fbt-zqz`. Branch: `ntm/fbittorrent/cod_3-p1-02b`.
Baseline: `64a2bcb9a4eb86f10973aa56f491442bd50383f5`.
Evidence root (`L`): `target/test-logs/fbt-p1-02b/`.

## Cause

This is a fixture readiness race, rather than an indefinitely stalled engine
resume or a teardown deadline. The test treated reopening the seed's listener
as proof that its restored torrent could serve payload. Restoration first checks
the files into Paused; periodic queue reconciliation subsequently applies saved
seeding intent and makes the handle Live. Reconnecting before that transition
enters normal peer error/retry backoff. Its first delay is 10 seconds plus jitter;
the remaining capped payload then has too little time in some 20-second windows.

The source explains the observed states: `Session::check_incoming_connection`
requires `live_wait_initializing` (`vendor/rqbit/librqbit/src/session.rs` around
827). Initialization ending in Paused does not satisfy that requirement.
`src/engine/queue.rs` applies running seed intent after checking; the test helper
uses production's one-second maintenance tick. The peer backoff configuration is
in `vendor/rqbit/librqbit/src/torrent_state/live/peer/stats/atomic.rs`, and the
retry task is in `live/mod.rs`. Those production paths are unchanged.

## Change and regression

The fixture explicitly pauses the client's old run, reopens the seed, waits for
the restored seed's **verified, Live, unpaused** state, then unpauses the client.
It observes the real maintenance result; it neither drives reconciliation itself
nor assumes a fixed sleep is enough. The 25 ms polling interval controls only
how soon an already true readiness condition is observed.

The completion allowance remains **20 seconds**, with elapsed client pause, seed
restart and readiness time subtracted. Readiness also uses that remaining
balance; client unpause and completion run inside the remaining timeout.
No completion window or shutdown budget was increased. The existing cap/burst,
partial-transfer, app-close, stopped-bytes, persisted-intent, payload equality,
exact final byte count and minimum capped-duration assertions remain. The
original metadata responsiveness test is byte-identical.

`restored_seed_readiness_waits_for_running_state` uses a real torrent and file
verification. Actual queue network policy holds the verified seed Paused. A
channel reports the readiness future's **actual first poll** as Pending, and a
second channel proves it has not completed. Clearing the network block admits
seeding; the waiter must then finish with the seed verified and Live. This
ordering has no scheduling sleep window.

The test-only `FBT_P102B_FORMER_ORDER` control restores the missing readiness
gate. The readiness regression then fails immediately, reporting Ready instead
of Pending while the seed is verified and Paused. `negative_readiness.jsonl`
expects native exit 101 at that exact assertion and rejects unrelated worker
failures. The same switch retains the old transfer operation order for the five
timeline controls; every original transfer assertion still runs there. This
switch exists only in the engine test include and is removed from the environment
for every normal invocation.
