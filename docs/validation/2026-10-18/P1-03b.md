# P1-03b — resolver cancellation and teardown joins

Bead: `fbt-e3e`. Branch: `ntm/fbittorrent/cod_3-p1-03b`.
Assigned main-derived baseline: `ab18299b5183948b4cd1a836bb95cc0812f0d952`.

The three acceptance criteria pass on the final source. The original retained
four-second runtime teardown timeout was **not reproduced** in the unchanged
baseline loops; this receipt does not attribute that particular timeout to a
specific nested tracker task. A controlled native scheduling regression does
reproduce the ownership violation with the former teardown order.

`AppEngine::drop` now cancels and joins restore attempts before stopping the
session or cancelling the application region. It also joins cancelled attempts
whose records were removed or retried. The current restore task structure,
restore decision, daemon lifecycle owner and instance-lock ownership are
unchanged. New admissions check `stopping` under the restore map lock. No
bookkeeping lock spans an await. Completed current handles are returned to the
map so existing `is_finished()` assertions remain meaningful. Errors and timeouts
remain failures. The existing shared four-second deadline is not increased.

The new regression observes a real 16-byte UDP tracker connect request from a
peerless magnet; the local tracker never responds. It wraps that real resolver's
join in an application-owned native task with a 25 ms cleanup epilogue. This
controlled epilogue widens the scheduling race, without replacing the resolver,
network effects or runtime. Phase 0 means waiting on the real resolver, 1 means
its join completed, 2 means cleanup completed under a live application context,
and 3 means that context was cancelled before cleanup completed. The common
production drain method is exercised with a 250 ms deadline; ordinary `drop`
uses four seconds and is separately measured by `bad_record_does_not_block`.
Removal and retry exercise the same invariant for superseded attempts.

## Scope, deviations and remaining uncertainty

`src/engine/restore.rs`, `src/engine/tests/{mod.rs,startup.rs}` and this receipt
changed. The orchestrator explicitly granted the overlap with P1-16; its dormant

including the worker-local compiler probe. There is no new stack capture naming

proves the cancellation/join ordering gap under controlled scheduling, and the
final loops prove the measured shutdown behavior; they do not establish the
historical timeout's unique root cause. If that exact deadline recurs, runtime
region/task attribution is the remaining follow-up. No other work was picked.

No release build, `all.sh`, merge, tracker edit or live-user-state access was
performed, per the orchestrator's debug-only instructions.
