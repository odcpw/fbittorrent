## P1-16c — Typed SetSeed uses the live cap setter (fbt-yur)

Branch `ntm/fbittorrent/cod_4-p1-16c-yur`, based on `b51420a` from main.

Typed `SetSeed` now saves the seed policy, cap and tags before calling
`ManagedTorrent::set_upload_bps` on the existing handle. It retains the handle,
metadata and verified data. Queue reconciliation applies pause/resume:
`stoppedUP` → `uploading` → `stoppedUP`, with `default_cap` → `unlimited` →
`default_cap`. A failed save restores the in-memory intent and attempts to
restore the previous durable intent before returning; the live setter is not
called on that failure path.

Dormant seed activation still admits and checks its data. It enters admission
with running intent, so reconciliation does not unpause and cancel an already
running initialization. The newly admitted handle then uses the same cap
setter. Other recheck/file-selection admissions retain their paused initial
intent. Unresolved magnets retain background restoration.

Two new engine tests instrument the production filesystem backend: every read
and storage creation is counted while all actual IO is delegated to
`FilesystemStorage`. The fixture is a real, private, one-piece five-byte torrent
with SHA-1(hello), no DHT, trackers, discovery or peers, and fastresume disabled.
Exactly one successful five-byte read is one real full checksum pass. This
detects extra checks that could fit between state observations.

- `typed_seed_live_retains_handle_and_never_checks`: one initial check; repeated
  typed seed-on/off calls preserve handle and metadata Arc identity, metainfo
  inode/mtime, completion, checked data, pause state and unrelated tags. The
  legacy states and normalized upload policies follow the sequence above.
  Failed saves in both directions leave disk and in-memory policy unchanged.
- `typed_seed_dormant_checks_once_then_retains_handle`: startup and seed-off
  create no storage or handles. Seed-on admits once, checks once, and starts
  verified seeding with unlimited policy. Repeated on/off calls retain that
  handle and the single-check count, with the expected cap and run state.

counts were `[2,2,10]` instead of `[1,1,5]`. Its 45-pass/1-fail output and
receipts remain under `initial-double-check/`. The fix admits dormant seeding
with running intent; the original exact one-check assertion remains unchanged.
Both final suites then passed.

No unmet criterion. No release build, all.sh or daemon replay was run, per the
engine-only instruction; legacy serialization was not changed. Existing P6-07
daemon cases remain untouched. No owner service or live torrent data was used,
and no lifecycle, instance-lock, vendor, tracker or shared validation-index
file was changed.

Follow-up noticed, not changed outside this bead: general queue reconciliation
can also unpause an initializing handle with paused intent. This change avoids
that cancellation/restart for dormant seed activation only; incomplete or
explicit recheck admission policy in `src/engine/queue.rs` / `restore.rs` may
need a separate review under load.
