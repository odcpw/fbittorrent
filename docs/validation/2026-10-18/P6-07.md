## P6-07 — Live per-torrent upload cap (fbt-p6-07-9bt)

Branch: `ntm/fbittorrent/cod_4-p6-07-9bt`, based on `ee2a214`.
The two behavioral acceptance criteria pass through the current native
IPC/CLI adapter. One wrapped `all.sh` and the release foreground harness are
green. The absent v1 adapter remains an integration boundary below.

The fork exposes `ManagedTorrent::set_upload_bps(Option<u64>)`. It validates
finite caps as 16384 through `u32::MAX` bytes/s; `None` means unlimited.
Per-torrent limiters now belong to the shared torrent options instead of a
temporary live state. Cap edits retain the handle and checked data, and the
same limiter survives pause/resume. Pending reservations re-read the limiter
after waiting. Repeating an unchanged managed-torrent cap does not reset its
bucket.

The engine validates and saves the record before updating this limiter under
the ledger lock. It returns acknowledgement synchronously, with no rebuild,
metadata replacement or hash check. Existing CLI seed/noseed use the same
upload-cap route. The fork README and `docs/IPC.md` document the change.

The current checkout has no daemon `serve`, ApiConn or NDJSON adapter. The two
named cases in `daemon.py` use its explicit current-engine adapter, a real
tmux TUI owner, real CLI/socket calls and actual loopback peer payload. This
is process-level native-engine evidence, not v1 protocol qualification. The
planned v1 adapter must map the acknowledgement to `{state: "done"}`, retain
the compatible `enum(done|pending)` result type, and route `set_seed` through
the setter. No new operation, capability or JSON field is advertised here.

Every run used the rch shim and `CARGO_BUILD_JOBS=4`. App/test processes used
five isolated XDG directories and disposable data; tmux used the bead-specific
session `fbt-fbt-p6-07-9bt` on a separate per-sandbox server. The 8 MiB seed/leech

The new engine test `upload_cap_edit_retains_handle_and_checked_data` checks
that finite/unlimited/repeated edits preserve `Arc` identity, checked data and
acknowledgement, update normalized cap fields and durable records, and reject
invalid values. A forced ledger-writer failure retains the old record and
handle. The fork test additionally tests the actual limiter configuration and
reservations rather than relying on ledger values.

The rate case measures byte deltas over one-second windows and records the
engine's reported download rate. The deadline starts before the cap request.
The reported rate must be within 25% of the requested cap before 5 s. Measured
byte windows must also enter their new rate band: 65536..262144 B/s for the
increase from 32768 to 131072, then 1..65536 B/s for the decrease to 32768.
Byte-window bands accommodate the initial token burst and chunk granularity
and exclude the previous steady cap. Every sample retains its monotonic time.
State polling and explicit snapshots record each engine; saved metainfo inode
and mtime must stay unchanged throughout. Unit handle/live-state identity
assertions additionally detect rebuilds too brief for polling.
