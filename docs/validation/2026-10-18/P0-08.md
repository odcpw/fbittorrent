## P0-08 — graceful shutdown on terminal close

Bead `fbt-p0-08-plg`, branch `ntm/fbittorrent/cod_3-p0-08-plg`, cut from local
main `70476b1`. The prior P0-07 branch is untouched. The orchestrator owns the
validation index, merge verification and bead closure.

### Instrumentation and chosen fix

The instrumented pre-fix probe in
`target/test-logs/fbt-p0-08-plg/hangup-baseline-native/` recorded SIGHUP but no
model shutdown hook or `drop(app)` event. At about 2.06 seconds the app exited
129 and released its lock; `engine.sock` remained at the six-second deadline,
and stderr contained no drain message. This selects the watchdog path from
the bead; the main loop cannot be relied on to observe the pending signal.

The public ftui `AppBuilder::run()` also calls `process::exit(128 + signal)`
after its own signal lifecycle. The app now uses `Program::run()`, which
returns control to its owner instead. The model acknowledges signals at the
Hover tick and shutdown hook, preserving the first signal for exit mapping
and for the watchdog if terminal teardown subsequently stalls.

`AppGuard` shares the engine owner through `Arc<Mutex<Option<_>>>`. Normal
teardown or the watchdog takes it exactly once. On a pending signal the
watchdog acknowledges immediately, drains the real engine in a worker,
continues acknowledging repeat signals during that drain, stops search
children, then exits `128 + signal`. The same guard covers the parked VPN
state. The engine reports `INFO engine drained in <ms> ms` only after both
session and runtime drain succeed; the existing four-second budget is shared
across those operations.

With `FBT_DEBUG_SIGNALS=1`, events append to the specified state file. The
signal-record marker observes ftui's pending slot at up to 10 ms polling
resolution. Runtime lifecycle markers use the public model shutdown hook
(begin) and `Program::run()` return (end); these bracket private ftui lifecycle
work rather than modifying registry sources. Absence of those markers in the
baseline is evidence, not an invented loop observation. Clear and app-drop
markers record the app's own operations.

The first two fixture attempts absorbed the terminal hangup in their waiter;
their `baseline*` and `instrumented-baseline*` logs are retained as fixture
failures and are not production failure evidence. The corrected supervisor
relays the hangup received from `tmux kill-window` to its app child and
captures the child's real wait status. The tmux window is actually destroyed.

### Real Ghostty check and remaining human observation

A disposable Ghostty 1.3.1+omarchy.3 window ran the final release binary as
its direct terminal child, with the same isolated storage and loopback-only
unfinished torrent. The window was identified by the unique application class
`org.omarchy.fbittorrent.p008`, its owned GUI PID and exact window address.
The application had an exclusive instance lock before close.

No human close confirmation arrived during the manual observation window.
That attempt timed out; its failed JSONL is retained in
`target/test-logs/fbt-p0-08-plg/ghostty-unobserved/` and is not a product
acceptance result. The first fallback command used obsolete Hyprland dispatch
syntax. Cleanup of that expired probe raced its still-live app; the owned
orphan was identified by its isolated XDG runtime and forcibly stopped.

The corrected additional automated check used Hyprland 0.56.2's
[graceful window-close dispatcher](https://wiki.hypr.land/Configuring/Basics/Dispatchers/),
with an explicit selector for only the test window:

```bash
hyprctl dispatch 'hl.dsp.window.close({ window = "address:<owned-test-window>" })'
```

The command exited 0. The real window closed and all four check steps passed:
the socket was absent and the lock free at the first post-window-close probe
(4 ms after observing closure; window polling has 100 ms resolution),
`tui.stderr` contained `INFO engine drained in 0 ms` (integer millisecond
resolution), and the signal trace recorded SIGHUP, acknowledgement and a
completed watchdog drain. Both app and GUI processes exited. No test window
or process remains.

The manual-check command was
`python3 target/test-logs/fbt-p0-08-plg/ghostty-check.py` (exit 1, timed out).
The additional automated command was
`python3 target/test-logs/fbt-p0-08-plg/ghostty-automated-check.py` (exit 0).
Both are retained one-off validation scripts, not default-suite tests. The
successful JSONL and stderr are archived in
`target/test-logs/fbt-p0-08-plg/ghostty-automated/`; the command and actor are
recorded in `ghostty-close-actor.json`. This desktop evidence is automated;
the bead's requested once-only human Ghostty close remains unperformed.

All three acceptance criteria are satisfied by the automated tmux route.
The additional Ghostty automation does not substitute for a human observation.
CI and post-merge qualification are not claimed. A follow-up worth testing
separately is IPC shutdown after external removal of a live runtime directory:
`Server::stop_accepting` currently ignores a failed pathname-based wake before
joining its listener. This change does not alter that IPC recovery behavior.
