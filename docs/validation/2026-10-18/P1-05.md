## P1-05 — API v1 contract types and shared fixtures

Bead: `fbt-p1-05-2qa`. Branch: `ntm/fbittorrent/cod_3-p1-05-2qa`.

The P1 contract now has strict serde arguments for all 22 operations, contextual
success-result decoding, typed error/failure envelopes, all 17 A.8 event shapes,
and the full P1 objects. `Torrent` mirrors the normalized P1-19 `TorrentView`
with the additive optional fields from Appendix A. There is no listener in this
change. The legacy IPC, engine lifecycle and instance-lock ownership are untouched.

`docs/IPC.md` is the maintained wire contract. The six shared NDJSON files contain
162 records: 54 requests, 97 server frames, five expected models and six first-line
volatile declarations. They cover all 22 P1 operations (including P1-14 log/stats),
all 17 event names and all 16 error codes. The hello fixtures include a synthetic
proto-2 reply for client mismatch banners. Errors include a null-ID invalid-args
reply and request-less error followed by bye. The gap fixture skips rev 4, preserves
the last accepted rev 3, requests unsubscribe/re-subscribe, and supplies a fresh
snapshot. Pending mutations include refs and done/failed/timeout outcomes.

Public interfaces for consumers:

- `api::{Request, Call}` and the argument structs in `api::request`;
- `api::{Success<T>, Failure, Response<T>, ResponseId, Error, ErrorCode}`;
  `Success<Reply>` serializes directly, checked for every fixture success;
- `api::Reply::decode(op, result)` checks the exact result shape using the preceding
  request's operation; successful responses carry no operation name themselves;
- `api::{Event, Item, StateData, Topic}`; `Event::validate()` checks topic/item
  compatibility, chunk bounds and conditional fields;
- the full objects in `api::objects`, constrained identifiers in `api::scalar`,
  and operation mutating/idempotent/since metadata in `api::ops::TABLE`.

Every optional field is omitted when absent. The explicitly nullable invalid-ID
response uses a dedicated enum, not an omitted Option. Upload-limit arguments
preserve omitted versus explicit null versus numeric value with `Update<T>`.
Open enum fields retain future strings; typed output objects accept unknown fields.
Request arguments reject unknown keys. The sentinel walker reports JSON pointers,
including array elements, rejects -1/8640000 and unknown-value zero/null substitutes,
and preserves observed zeros with provenance (rates, known initial progress, live
peer counts and ratios with downloaded bytes). Canonical round trips sort every
object recursively and serialize without whitespace.

### Scope and limits

The orchestrator explicitly authorized exactly `mod api;` in `src/main.rs`; that
single line is the entire main.rs diff. The validation README index is unchanged.
No unmet acceptance criteria. No release build or all.sh was run, following the
orchestrator's latest contract-only validation instruction. These are typed
contract checks, not live daemon replay or UI reducer proof: those belong to
P1-06 and P2-02 respectively. The expected models define partial store assertions,
not a second production store implementation.

Follow-up noticed, not implemented: PLAN section 3.4.1 describes an unbounded
collection-result exception for torrents.list/files, while the bead's copied
transport rule and Appendix A.1 state a 1 MiB output cap. IPC.md and the fixture
checks retain the bead's hard cap. The server owner should reconcile that
collection-limit discrepancy before implementing live response framing.
